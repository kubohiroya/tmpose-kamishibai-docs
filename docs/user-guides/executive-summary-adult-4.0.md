## 概要

TMPose紙芝居4.0は、物語を見るだけでなく、参加者の操作や身体の動きを物語の進行へ結び付けられる
参加型デジタル紙芝居です。背景、登場人物、セリフ、音、画面効果、条件分岐、キー・タッチ・ポーズ入力を、
YAMLで書いた台本と画像・音声・ポーズモデルから構成します。

作者は作品ごとのプロジェクトディレクトリを正本として管理します。台本を検証してプレビューし、上演に使う
自己完結SB3をビルドするまで、同じDSL 4.0の契約を使用します。標準的な作品を作るために、作者が
TurboWarpのブロックを作品ごとに組み替えることは想定していません。

この文書は、DSL 4.0で何ができるか、作品がどのように実行されるか、教育活動へどう取り入れられるかを
説明する概要です。フィールドやアクションの詳細は、末尾の台本作成ガイドとスキーマリファレンスで確認してください。

## このアプリの価値

### 物語と素材を一つのプロジェクトとして扱える

作品の正本には、起点のYAML、画像、音声、ポーズモデル、`project.source.json`を含めます。規模が大きい
作品では、台本を複数のYAMLへ分割できます。素材と、それを物語のどこで使うかがプロジェクト内で対応するため、
共同制作でも変更対象と結果を確認しやすくなります。

### 身体参加を物語上の出来事にできる

参加者が指定されたポーズを取る、キーを押す、画面へ触れるといった行為を、シーンの進行や分岐へ
つなげられます。参加者の動きは単なる操作ではなく、「登場人物を助ける」「扉を開ける」など、物語上の
意味を持つ出来事として設計できます。

### 制作中の失敗を上映中の作品から分離できる

制作中に書きかけの台本や不足した素材が見つかっても、直前に正常だったプレビューを壊しません。
作者は問題のあるファイルと位置を示す診断を読み、正常な作品を保ったまま修正できます。

### 制作と配布で同じ契約を使える

制作中のプレビューと配布物のビルドは、同じDSL 4.0の台本と検証規則を使います。
制作時だけ通る独自形式へ書き換えず、確認した台本と素材から配布物を作れます。

## 人・AI・プログラムの役割

4.0を使った制作では、人、AI、プログラムの役割を分けて考えます。AIが物語や上映結果を自動的に決めるのではなく、
人が目的と安全条件を決め、AIが素材作りやポーズ分類を補助し、プログラムが検証済みの台本だけを実行します。

| 担当       | 主な役割                                               | 確認すること                                                 |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------ |
| 人         | 物語、場面、使うポーズ、参加方法、安全な運営を決める   | AIの出力と上演結果が意図に合うか                             |
| AI         | 画像を生成する、カメラ映像のポーズを分類する           | 誤生成や誤認識が起こり得ることを前提に、人が結果を確認したか |
| プログラム | YAMLと素材を検証し、宣言されたアクションを順に実行する | 不完全な台本を実行せず、診断と代替操作を提示できるか         |

教材やワークショップでは、この分担そのものを学習対象にできます。参加者は、AIの出力をそのまま採用するのではなく、
プロジェクトへ保存した素材を確認し、台本と組み合わせ、プレビューで結果を確かめます。

## 制作のサイクル

作品制作は、一度で完成させる作業ではありません。次の小さなサイクルを繰り返し、物語と参加方法を改善します。

1. 物語、場面、登場人物、ポーズや代替操作を設計する
2. YAMLソース、画像、音、ポーズモデルなどをプロジェクト内で編集する
3. `validate`でYAMLの構造、スキーマ、参照関係を検証する
4. Web PreviewまたはCLIプレビューで、実際の進行、入力、見え方、音を確認する
5. 上演結果と参加者の反応をもとに、設計または素材へ戻る

検証に失敗しても、直前の正常なプレビューは保たれます。作者は診断から修正箇所を確認し、
もう一度検証できます。配布するときは、同じプロジェクトを再検証してから自己完結SB3をビルドします。

## 安全に参加するために

安全は、作品が技術的に動くことと同じ重さで計画します。AIが作った画像や台本、ポーズ認識の結果は、
意図どおりか、差別的・攻撃的な内容や個人情報を含まないかを人が確認してから使います。

カメラを使う場合は、目的、映る範囲、保存や外部送信の有無を参加者と保護者へ事前に説明し、同意を確認します。
設置場所、照明、周囲の映り込みも本番環境で確認してください。カメラを使わない作品も正式な選択肢です。
身体参加が活動目的に合わない場合や同意を得られない場合に備え、同じ場面をキーやタッチでも進められるようにします。

後続文書を読みやすくなります。

Source Graphは、起点のYAMLから`include`で到達する複数ソースの関係全体です。
`StoryDocument`は、構文・スキーマ・参照関係の検証を終えた実行用の台本です。作者向け文書では
プロジェクトとSource Graphの作り方を、開発者向け文書では`StoryDocument`の生成と実行を詳しく扱います。

ソースフロントエンドは、YAMLの構文、スキーマ、参照関係を検証し、成功した台本だけを変更不能な
`StoryDocument`へ正規化します。検証中の入力は候補（candidate）、同じ時点で安定して取得したソースと素材の組は
世代（generation）と呼びます。候補の検証に失敗しても、直前の正常な世代を置き換えません。

## プロジェクトとYAML台本

小さな作品は、次のようなディレクトリから始められます。

```text
tutorial-story/
├── project.source.json
├── story.k4.yml
├── beach.svg
├── opening.mp3
└── rescue-pose/
    ├── model.json
    ├── metadata.json
    └── weights.bin
```

`project.source.json`は起点となるソースを一つに決めます。新規プロジェクトでは、UTF-8の`story.k4.yml`を
起点にする構成を推奨します。YAMLでは、アセット、Actor、表紙、表示スタイル、変数、操作、分岐、シーン、アクションを
名前付きの構造として記述します。

```yaml
kamishibai: '4.0'

assets:
  Beach: backdrop
  HeroIdle: costume:Hero

actors:
  Hero: HeroIdle

scenes:
  opening:
    - stage: Beach
    - Hero.say:
        text: こんにちは！
        seconds: 2
```

一つのアクションには命令を一つだけ書きます。意味の異なる複数の引数には、`text`や`seconds`のような名前を
付けます。未知のキー、型の違い、存在しないアセットやシーンの参照は、実行を始める前に診断されます。

## Source Graphで物語を分割する

`include`を有効にすると、起点のソースから到達する複数のYAMLを、一つのSource Graphとして合成できます。
章や場面ごとにソースを分けても、最終的には一つの`StoryDocument`として検証・実行されます。

Source Graphは、後から読んだ定義で暗黙に上書きしません。重複ID、単一設定の重複、循環する`include`、
プロジェクト外へ出るパスをエラーにします。ソース件数、バイト数、`include`の深さにも有限の上限を設けます。
取り込まれたソースで宣言したローカル素材は、そのソースのディレクトリを基準に解決されます。

プレビューとビルドは、到達するソースと参照されたローカル素材を一つの世代として安定取得します。
台本だけ、または素材だけが新しい途中状態を部分的に実行しないことが、共同編集や授業中の試行錯誤を
安全に行うための重要な境界です。

## 制作・確認・配布の方法

| 利用形態      | 役割                                                                                                                 |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| Web Preview   | 対応ブラウザーでプロジェクトディレクトリを読み取り専用で選択し、外部エディターで保存した変更を検証して再読み込みする |
| CLI検証       | `validate-dsl4`で台本を副作用なしに検証し、人向けまたはツール向けの診断を出力する                                    |
| CLIプレビュー | `preview-dsl4 --watch`でローカルプロジェクトを監視し、ブラウザー上のランタイムへ正常な世代を渡す                     |
| CLIビルド     | `build-dsl4`でソースとローカル素材を再検証し、自己完結SB3を不可分に出力する                                          |
| 公開アプリ    | 検証済み`StoryDocument`をランタイムとプラットフォームアダプターで実行する                                            |

Web PreviewとCLIプレビューは、制作中の確認に使う画面です。YAMLやアセットを保存すると、正常な候補だけが
再読み込みの対象になります。作品の先頭、現在のシーン、または条件を満たす現在のアクションから再開できます。
監視用の接続機能、認証トークン、再読み込みダイアログの状態は配布成果物へ含めません。

ビルドはディスク上の候補をもう一度検証してから出力先を置き換えます。ローカルのソースと素材を含む
自己完結SB3は、TurboWarp Editorでの確認やWeb Player／Packagerへの入力に利用できます。ビルドが失敗した場合は、
既存の正常な出力を保持します。

## 物語が実行される仕組み

DSL 4.0の処理は、次の責務に分かれています。

```text
YAMLプロジェクト・Source Graph
        ↓ 安定取得
YAML解析・スキーマ検証・意味検証
        ↓ 正規化
変更不能なStoryDocument
        ↓
ランタイムコントローラー
        ↓
TurboWarp、カメラ、音声、TMPose等のプラットフォームアダプター
```

ランタイムコントローラーはシーンとアクションの順序、分岐、入力、停止を管理します。背景の切り替え、Actorの表示や移動、
セリフ、音、画面効果、ポーズ認識など、環境へ依存する処理はプラットフォームアダプターを介して実行します。この分離により、
物語の意味とブラウザーやTurboWarp固有の操作を混在させずに検証できます。

入力も一つの時系列として扱います。同じキーやタッチが、作品内の選択と運営者用navigationの双方へ同時に
消費されないよう、その時点で意味を持つ一つの受け手へ渡します。

## カメラとポーズ認識

ポーズ認識を使うシーンでは、プロジェクトに登録した`poseModel`をTMPoseアダプターが読み込み、カメラ映像から得た
分類結果を物語のアクションへ渡します。成功したポーズに応じてコスチュームや音を変え、次のシーンへ進められます。

カメラプレビューには、左右反転の既定値とシーンごとの指定を持てます。必要に応じて、参加者や会場に合わせて
プレビューの左右反転を切り替えるボタンや、使用するカメラを選ぶメニューも構成できます。端末固有のデバイスIDは
台本や`StoryDocument`へ保存せず、実行セッション内で扱います。

ポーズ認識を利用するときは、次を運用計画に含めます。

- カメラを使う目的と映る範囲を参加者・保護者へ事前に説明する
- ブラウザーのカメラ許可、設置位置、照明、背景、参加人数を本番環境で確認する
- 左右反転後の見え方と、カメラ選択メニューの操作をリハーサルする
- 認識しにくい場合にキーやタッチで進める代替手段を用意する
- 終了・停止時にカメラ、モデル、音、リスナー等の資源を解放できることを確認する

カメラを使わない作品も作れます。身体参加が活動目的に合わない場合や、カメラ利用への同意を得られない場合は、
キー・タッチ入力や時間進行を選びます。

## 教育・ワークショップでの利用

### 物語を構造へ分解する

学習者は、物語をシーン、登場人物、アクション、条件、入力、結果へ分解します。「何が起きたら、誰がどう動き、
次にどこへ進むか」をYAMLの名前付きフィールドで表す過程は、物語理解とプログラミング的思考を結び付けます。

### 役割を分担して共同制作する

物語を考える人、画像や音を作る人、ポーズを設計・学習する人、YAMLを編集する人、プレビューで検証する人に
役割を分けられます。Source Graphを使えば、章や場面を分担しながら、一つの作品として重複や参照漏れを
検査できます。

### AIの役割と限界を観察する

画像生成やポーズ分類を取り入れる活動では、人が物語と評価基準を決め、AIの出力を確認し、プログラムが
検証済みのアクションを実行するという役割の違いを扱えます。認識が照明、姿勢、服装、背景などに影響されることを
観察し、代替操作や再試行を設計することも学習になります。

### 発表を共同体験にする

代表者がカメラの前でポーズを取り、ほかの参加者が次の展開を予想したり応援したりすることで、作品発表を
共同体験にできます。国語、情報、総合学習、演劇的表現、地域紹介、外国語活動などを横断した教材にできます。

上映環境のネットワーク条件も確認します。オフライン運用ではローカル素材を成果物へ含めます。

1. 作品を作る場合は[紙芝居DSL 4.0 台本作成ガイド](../dsl-author-guides/dsl-4.0-author-guide.md)で、最小台本から順に実践する
2. 作成中に型や必須性を調べる場合だけ[紙芝居DSL 4.0 Schemaリファレンス](../dsl-author-guides/dsl-4.0-schema-reference.md)を引く
3. 教材設計や制作環境を詳しく検討する場合は[TMPose紙芝居 4.0 アプリ・教材・ツールチェインガイド](../developer-guides/application-materials-guide-4.0.md)で、人・AI・プログラムの分担、プレビュー、ビルドを確認する
4. 実装を保守する場合は[紙芝居アプリ 4.0 ソフトウェアメンテナンスガイド](../developer-guides/developer-guide-4.0.md)から開発者向け文書へ進む

- [DSL 4.0 Source Graph Preview](https://github.com/kubohiroya/tmpose-kamishibai/blob/79457815f5c89b181b1a879a079a4d6a72d405ed/docs/design/dsl-4-source-include-preview.md): 複数ソース、トランザクション、有限上限、ロールバックの設計
